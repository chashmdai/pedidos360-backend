Evidencia E-08. Grupos de consumidores y distribución de particiones

Objetivo
Mostrar los tres grupos, su asignación de particiones, offsets y lag.

Indicador asociado
EP5: consumidores (14 %); consumer groups (12 %). EP6: métricas de offsets y lag (15 %).

Entorno
AWS cuenta 647660738152 (us-east-1), EC2 i-01bcf3ef9d3a64d4e (t3.large, Ubuntu 24.04), release ep5-20261119T040026Z; comandos ejecutados como root en /opt/pedidos360/current mediante SSM Run Command (AWS-RunShellScript, script revisado deploy/ep5-evidence.py). Kafka UI consultado por su API en 127.0.0.1:8090 desde la propia instancia (la misma vista que se abre por reenvío de puertos SSM).

Resultado esperado (informe)
Agregador con tres miembros y una partición cada uno; monitor y vista con un miembro y tres particiones; lag 0 en reposo.

Resultado observado
Los tres grupos están STABLE con asignador cooperative-sticky. pedidos360-sales-aggregator tiene 3 miembros (sales-aggregator-0..2) con una partición cada uno (0, 1 y 2). pedidos360-order-monitor tiene 1 miembro con las particiones 0, 1 y 2 de orders.registered.v1, y pedidos360-sales-dashboard 1 miembro con las particiones 0, 1 y 2 de product-metrics.v1. Lag 0 en todas las particiones con offsets confirmados, después de 5 pedidos, 1 registro inválido y 1 duplicado. Kafka UI → Consumers muestra lo mismo (members, state y consumerLag 0). La partición 0 de product-metrics.v1 aún no recibe claves, por eso no tiene offset confirmado ('-'): no es lag.

Diferencias con el informe
Ninguna en el resultado. La parte Kafka UI se registra como texto desde la API de Kafka UI (/api/clusters/...), con sesión LOGIN_FORM abierta en la propia instancia: es la misma información que muestra la pantalla al abrirla por reenvío de puertos SSM a 127.0.0.1:8090. Una partición sin mensajes aparece con CURRENT-OFFSET '-' y no con 0, porque el grupo aún no confirma offsets en ella; no es lag.
