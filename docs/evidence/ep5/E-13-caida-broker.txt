Evidencia E-13. Tolerancia a la caída de un broker

Objetivo
Verificar la continuidad del servicio con un broker detenido.

Indicador asociado
EP6: arquitectura Kafka (10 %); justificación de réplicas (10 %).

Entorno
AWS cuenta 647660738152 (us-east-1), EC2 i-01bcf3ef9d3a64d4e (t3.large, Ubuntu 24.04), release ep5-20261119T040026Z; comandos ejecutados como root en /opt/pedidos360/current mediante SSM Run Command (AWS-RunShellScript, script revisado deploy/ep5-evidence.py). Kafka UI consultado por su API en 127.0.0.1:8090 desde la propia instancia (la misma vista que se abre por reenvío de puertos SSM).

Resultado esperado (informe)
Las particiones lideradas por el broker 2 cambian de líder; ISR de dos réplicas; el pedido se publica y procesa. Tras el inicio, el ISR vuelve a tres réplicas.

Resultado observado
Antes: orders.registered.v1 p0 líder 2, p1 líder 3, p2 líder 1; product-metrics.v1 p0 líder 1, p1 líder 2, p2 líder 3; ISR de 3. Con docker stop kafka-2, las particiones lideradas por el broker 2 cambiaron de líder (orders p0 → 1; metrics p1 → 3) y todas quedaron con ISR de 2 réplicas, lo que aún cumple min.insync.replicas=2. Con kafka-2 detenido, el usuario registró 1 × Taza (a4b808ee…, 14:29:32Z). Orders lo publicó (PUBLISH_CONFIRMED partition=2 offset=2, 0,93 s después del commit), los tres grupos lo procesaron y Taza quedó en 4 u / 3 pedidos / 51.960,00 (version 3), con lag 0. La vista mostró 114.890 CLP y 11 unidades. Con docker start kafka-2, el contenedor pasó a healthy, el ISR volvió a 3 réplicas en todas las particiones y el broker 2 recuperó el liderazgo de sus particiones preferidas.

Diferencias con el informe
Ninguna.
