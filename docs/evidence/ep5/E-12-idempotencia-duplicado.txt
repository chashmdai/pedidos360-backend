Evidencia E-12. Idempotencia ante un evento duplicado

Objetivo
Comprobar que una reentrega no duplica acumulados.

Indicador asociado
EP5: manejo de errores (12 %); consumidores (14 %).

Entorno
AWS cuenta 647660738152 (us-east-1), EC2 i-01bcf3ef9d3a64d4e (t3.large, Ubuntu 24.04), release ep5-20261119T040026Z; comandos ejecutados como root en /opt/pedidos360/current mediante SSM Run Command (AWS-RunShellScript, script revisado deploy/ep5-evidence.py). Kafka UI consultado por su API en 127.0.0.1:8090 desde la propia instancia (la misma vista que se abre por reenvío de puertos SSM).

Resultado esperado (informe)
Log CONSUME_DUPLICATE con el eventId; los acumulados no cambian.

Resultado observado
Se leyó el registro ya procesado del pedido d9d1058b… (partición 2, offset 0, eventId 4e172649-cccf-4f45-88a1-1ca5bbe0d10b) y se republicó con la misma clave y el mismo payload (quedó en p2, offset 1). Resultado: CONSUME_DUPLICATE eventId=4e172649… group=pedidos360-sales-aggregator ... code=ALREADY_PROCESSED. product_sales_daily no cambió (Café 5/2/44.950 v2, Taza 3/2/38.970 v2) y processed_stream_event siguió en 2. order-monitor lo evaluó otra vez (NO_ALERT): el monitor no acumula. Por diseño, ante un duplicado el agregador republica el estado vigente con la misma version, para cubrir una publicación fallida después del commit. La vista descartó esas copias como STALE_VERSION_DISCARDED version=2, así que los acumulados no cambiaron.

Diferencias con el informe
Ninguna en el resultado. Se documenta además que, ante el duplicado, el agregador republica el estado vigente con la misma version (recuperación ante una publicación fallida después del commit) y que la vista descarta esas copias (STALE_VERSION_DISCARDED).
