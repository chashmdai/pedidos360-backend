Evidencia E-15. Reconstrucción de la vista desde el tópico compactado

Objetivo
Demostrar el uso de la compactación para recuperar estado.

Indicador asociado
EP6: administración de Kafka (15 %); casos de uso (15 %).

Entorno
AWS cuenta 647660738152 (us-east-1), EC2 i-01bcf3ef9d3a64d4e (t3.large, Ubuntu 24.04), release ep5-20261119T040026Z; comandos ejecutados como root en /opt/pedidos360/current mediante SSM Run Command (AWS-RunShellScript, script revisado deploy/ep5-evidence.py). Kafka UI consultado por su API en 127.0.0.1:8090 desde la propia instancia (la misma vista que se abre por reenvío de puertos SSM).

Resultado esperado (informe)
Tras el reinicio, el grupo de la vista relee product-metrics.v1 desde el inicio y presenta los mismos acumulados.

Resultado observado
Antes del reinicio, la vista mostraba Café 7 u / 4 pedidos / 62.930 y Taza 4 u / 3 pedidos / 51.960 (total 114.890 CLP, 11 unidades). Tras systemctl restart pedidos360-sales-stream (UP en 17,5 s), el log muestra DASHBOARD_REBUILD group=pedidos360-sales-dashboard partitions=[...-0, -2, -1] from=beginning, y la vista releyó product-metrics.v1 desde el offset 0 hasta Café version 4 y Taza version 3. Las dos copias de version 2 que dejó E-12 se descartaron (STALE_VERSION_DISCARDED). Lag 0. El usuario recargó la vista y confirmó que las cifras coinciden.

Diferencias con el informe
Todavía no ha corrido la compactación: el segmento activo se cierra a la hora (segment.ms=3600000), así que la reconstrucción leyó todas las versiones y no solo la última por clave. El resultado es el mismo porque la vista conserva la version mayor de cada clave. Las alertas recientes no se reconstruyen: se guardan en memoria y el monitor inicia en latest, una limitación declarada en el informe ('Las alertas se conservan en memoria y se pierden al reiniciar el servicio').
