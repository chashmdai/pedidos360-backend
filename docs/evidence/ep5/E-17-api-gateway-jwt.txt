Evidencia E-17. API Gateway y validación JWT de la nueva ruta

Objetivo
Comprobar la protección de GET /api/v1/ventas/en-vivo.

Indicador asociado
EP6: API Manager valida JWT; frontend consume a través del API Manager; OAuth 2.0/OIDC.

Entorno
AWS cuenta 647660738152 (us-east-1), EC2 i-01bcf3ef9d3a64d4e (t3.large, Ubuntu 24.04), release ep5-20261119T040026Z; comandos ejecutados como root en /opt/pedidos360/current mediante SSM Run Command (AWS-RunShellScript, script revisado deploy/ep5-evidence.py). Kafka UI consultado por su API en 127.0.0.1:8090 desde la propia instancia (la misma vista que se abre por reenvío de puertos SSM).

Resultado esperado (informe)
HTTP 401 en los dos primeros casos; HTTP 200 con token válido emitido por Entra ID mediante authorization code con PKCE.

Resultado observado
Las tres solicitudes sin token válido fueron rechazadas por el autorizador JWT de API Gateway (az3h2vqgsi, autorizador 0ue6up) con HTTP 401 y latency 0, sin llegar al backend: (1) sin Authorization (sonda de scripts/ep5-verify-gateway.py, 12:48:15.526Z); (2) con un bearer inválido (12:48:15.895Z); (3) solicitud repetida por el usuario desde la pestaña Red del navegador, que la reenvía sin el header Authorization (14:04:48.179Z). Las sondas también dieron 401 en /productos, /pedidos y /me, con y sin bearer inválido. Desde la SPA en /app/, con sesión institucional obtenida por authorization code con PKCE (MSAL), la vista hizo 534 consultas GET /api/v1/ventas/en-vivo con HTTP 200, y el usuario verificó en el navegador el 200 y el header Authorization: Bearer. Las 124 respuestas 502 corresponden a la detención controlada de sales-stream en E-10.

Diferencias con el informe
Ninguna en el resultado. Además de los dos casos del informe, se registra un tercer 401 sin token (solicitud repetida desde la pestaña Red del navegador). El 404 de GET /app/{proxy+} del log es la sonda manual de /app/favicon.ico, corregida después con el ícono embebido (release ep5-20261119T144015Z).
